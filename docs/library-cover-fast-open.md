# Library cover reuse

The Library keeps the same three art-region snapshots in PSRAM. Replacement protects the newest snapshot of the other screen: cycling through Home layouts no longer evicts the last Library view, and Library paging preserves the last Home view. Text, selection and status are still redrawn. Catalog/art revisions, geometry, orientation and inversion retain their existing invalidation rules. A storage remount also invalidates retained pixels and cover-prefetch entries. No framebuffer or display refresh is added.

Native thumbnails retain their existing BMP prefix, packed-pixel trailer and checksums. A 24-entry fixed table (96-byte exact thumbnail paths, about 3.5 KiB of internal metadata) remembers successful source validation within a boot. The resource/media stamp is captured before opening the file, preventing a replaced open handle from being associated with a new path revision. Reuse requires an identical path, native key, full file size, footer fields, resource revision and media revision. Longer paths and exhausted revision counters use full source validation. The packed-pixel checksum is always checked before copying to the framebuffer. Direct loads and idle prefetch share validation results.

HalStorage supplies boot-local content/resource/media revisions without SD reads. Canonical reading-state and derived-cache writers preserve the resource revision; unknown or resource mutations and media changes invalidate cover-source reuse. Revisions saturate to zero instead of reusing an old value. A relevant mutation observed during a load prevents publication of its native pixels. Progress persistence through the typed reading-state path does not force cover-source revalidation. A retained, correctly keyed art snapshot can avoid that load entirely. See [Home and EPUB work reuse](home-epub-speed.md) for state-revision ownership.

All filesystem mutations must continue through HalStorage/HalFile; USB raw access invalidates media and requires the existing reboot. Host simulator storage reports zero revisions because host files can change outside its HAL, so it uses conservative fallback. The simulated visual output is preserved; these caches are tested separately by host fixtures.

RenderLock owns the source-validation table, scene cache and prefetch jobs. HAL revision counters are atomic and mutations remain under the storage mutex. The table stores metadata only: it does not add a per-cover pixel allocation. Existing 32 KiB preparation and 128 KiB prefetch arenas keep their bounds and PSRAM-only placement. The prefetch object adds a bounded path/stamp record; no per-row allocation or additional task is introduced.

Run `python host-tests/library-cover-fast-open/run.py` and `python host-tests/reader-performance/run.py`. Reuse tests compare the actual prepared pixels with normal rendering across orientations/polarity/palettes/row order; verify zero cover opens on retained-view return; test writes preserving source size/date, payload corruption, remount, interrupted loads, counter saturation and OOM. In the synthetic 240x300 source case, native reopen reads 2,709 bytes instead of 12,371, preserving identical pixels. This is an I/O count, not a device latency claim.

The development trace adds `cover_source_reuse`, `cover_source_read`, `cover_scene_hit` and `cover_scene_miss`. Release builds keep the trace hooks disabled. Measure both final visible presentation and SD bytes/calls. On X4 Pro, compare first open and repeated Home/Library returns with the same visible covers, then page forwards/backwards and change orientation, inversion, filters and cover resources. Expect unchanged pixels, correct covers and progress, and no growing heap loss. A retained-view hit should read no cover files. After regeneration, file transfer, cache clearing or remount, old art must not reappear. Physical latency and panel quality still require device testing.
